# نقشه‌ی راه EnterpriseMessenger

هدف: پیام‌رسان سازمانی برای حدود ۱۰ هزار کاربر، با تجربه‌ای روان مثل تلگرام برای ارسال و دریافت، جستجو و کار آفلاین، و در ادامه اتصال به نرم‌افزارهای حسابداری، گردش کار و قابلیت‌های هوش مصنوعی.

**قواعد کار**

- هر مرحله یک برنچ و یک PR به `develop` است. برنچ‌ها از `develop` گرفته می‌شوند و CI باید سبز باشد.
- هر فاز یک «شرط پایان» دارد. تا آن شرط برقرار نشده، فاز بعدی شروع نمی‌شود.
- پایان هر فاز: انتشار نسخه از `develop` به `master` و به‌روز کردن همین فایل و `CLAUDE.md`.
- زمان‌ها تخمین تقریبی برای یک برنامه‌نویس است. بعد از فاز ۲ که عدد واقعی داریم، دقیق‌تر می‌شوند.

**اهداف قابل اندازه‌گیری**

- زمان ارسال پیام تا نمایش برای گیرنده: زیر ۲۰۰ میلی‌ثانیه در صدک ۹۵
- باز شدن چت از کش محلی: زیر ۱۰۰ میلی‌ثانیه
- همگام‌سازی بعد از یک روز آفلاین: زیر ۲ ثانیه

## فاز ۳: کلاینت local-first (حدود ۲ تا ۳ هفته)

مهم‌ترین فاز برای حس روانی. الان کلاینت به شکل «اول کش، بعد شبکه» کار می‌کند: منبع اصلی داده signalها هستند، Dexie فقط کش است، و با باز شدن هر چت همه‌ی پیام‌های کش‌شده‌ی آن با `toArray()` خوانده می‌شوند.

| مرحله | کار |
| --- | --- |
| 3.1 | Dexie نسخه‌ی ۲: ایندکس `[conversationId+sequenceNumber]` و مهاجرت داده. فراخوانی `storage.persist()`. پاک شدن داده با خروج از حساب. سقف نگهداری داده |
| 3.2 | لیست پیام‌ها از `liveQuery` با پنجره‌ی صفحه‌بندی‌شده. state فقط وضعیت رابط کاربری را نگه می‌دارد |
| 3.3 | لیست گفتگوها از `liveQuery` و پیش‌بارگذاری چت‌های بالای لیست |
| 3.4 | virtual scroll برای پیام‌ها با ارتفاع متغیر |
| 3.5 | موتور sync در Worker. فقط یک تب sync می‌کند (Web Locks و BroadcastChannel). تشخیص gap روی `eventId` کاربر |

**شرط پایان:**
- باز شدن چت از کش زیر ۱۰۰ میلی‌ثانیه، حتی آفلاین.
- در تست e2e با قطع اتصال وسط ارسال، هیچ پیامی گم نمی‌شود.
- با چند تب باز فقط یک اتصال sync وجود دارد.

## فاز ۶: لایه‌ی یکپارچه‌سازی (حدود ۳ تا ۴ هفته)

پیام‌رسان نقش یک پلتفرم را دارد، نه میزبان گردش کار. اتصال به هر نرم‌افزار، یک adapter جداگانه است.

| مرحله | کار |
| --- | --- |
| 6.1 | حساب bot با API key و دسترسی محدود |
| 6.2 | webhook امضاشده (HMAC) با retry، و رویدادهای خروجی از outbox |
| 6.3 | پیام ساختاریافته (`Type` و `Payload` به شکل JSON) و دکمه‌هایی که callback برمی‌گردانند، مثل کارت تأیید فاکتور |
| 6.4 | اولین adapter حسابداری به‌صورت سرویس جدا که فقط از API عمومی استفاده می‌کند |
| 6.5 | اتصال به موتور گردش کار سازمان، یا Elsa اگر سازمان موتوری ندارد |
